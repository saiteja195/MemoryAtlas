# Upload sources and Atlas chat: design

Status: draft for approval. Branch: `feature/upload-and-chat`. Scope: **strict** (see Non-goals).

## Intent

Today the demo day is scripted: hand-written perceptions and transcripts stand in for what Muse
vision and Voice Transcribe would return. The "Use of Meta AI tooling" criterion is 25% of the
score, so the app needs a real path where a user adds their own photo, video, voice or text and
Muse reads it. Separately, asking questions feels like a log: one card per question, no sense
of a conversation, no progress while Muse works.

Two features:

1. **Add memory.** The user drops a file or types a note. Muse extracts what it can (time, place,
   activity, people, visible text). It asks the user only about what it is unsure about. After the
   user answers and presses Save, the result is stored through the existing capture gateway and
   compiler, so it lands in the temporal graph with provenance.
2. **Atlas chat.** The Ask panel becomes a conversation: bubbles, visible progress steps,
   answers with source chips and a status badge, tappable follow-up questions, a proper empty
   state, and a phone layout.

## Goals

- A user can add a photo, a voice recording or a text note and see it in the Atlas, using live Muse.
- Muse proposes metadata. The user confirms or fills gaps. Nothing is stored before Save.
- Chat reads as a conversation and shows what Muse is doing while it works.
- Every privacy decision stays in deterministic code.

## Non-goals (strict scope)

- No changes to the graph view, timeline, dashboard, consent panel or receipts, and no new graph
  highlight or pulse behaviour. After Save, the existing graph refresh is all that happens.
- No change to the compiler's extraction logic, the recall investigator or the eval harness.
- No video analysis in this slice (see Decisions, D3). The Add dialog says video is not
  supported yet instead of failing silently.
- No accounts, no multi-user, no cloud storage of media.

## Anti-goals

- Raw bytes being stored or logged. `media_bytes_retained` stays 0.
- The model deciding who consented, who may see data, or what is deleted.
- A flow that saves a half-understood memory without the user seeing it.

## Constraints

- `CLAUDE.md`: the LLM proposes claims and plans queries. Deterministic code decides storage,
  visibility and deletion. Consent questions are therefore generated by code from the
  participant list, not by the model.
- Commits only as `saiteja195`, no attribution trailers. Branch `feature/*`.
- Replay mode must keep working with no key. Add-memory in replay mode uses a small set of
  recorded or fixture perceptions and says so; chat keeps its current replay behaviour.
- Existing tests must stay green (`make test`).

## Design

### Two-phase add flow

The current `POST /capture/{kind}` ingests immediately. The new flow adds a **preview** phase
that stores nothing.

1. `POST /capture/preview` (multipart: one file or a text note, plus optional hints). The backend:
   - reads cheap metadata deterministically: EXIF capture time and GPS for images, file
     modified time as a labelled fallback, duration for audio;
   - calls Muse: `describe_image` for photos, `transcribe` (diarized) for WAV audio, plain
     text passed through for notes;
   - returns a **draft**: `fields` (when, where, doing, people), each with a value, a `source`
     (`exif`, `image`, `voice`, `note`, `user`) and a `confidence` of `sure`, `check` or `ask`;
     plus `questions`; plus a short-lived `draft_id`.
   - Raw bytes are held in memory only for the call and dropped. The draft carries text only.
2. The UI shows the draft and the questions. The user answers.
3. `POST /capture/commit` with `draft_id` and the answers. The backend builds a `RawCapture`
   from the draft text plus answers (using `perception` / `turns`, which the gateway already
   accepts, so no second Muse call) and runs the existing `engine.ingest`.

Why preview/commit instead of one call: the user must see and correct what Muse understood
before anything is stored, and the gateway rejects without consent anyway.

### Who decides which questions are asked

- **Model-proposed fields** carry `sure` / `check` / `ask` from Muse's own output plus
  deterministic rules (no GPS and no place in the image gives `ask` for Where; an OCR string
  that is only a prefix gives `check` and a yes/no confirmation).
- **Consent questions are code.** If the draft has more than one speaker or a visible person, the
  UI must collect, for each other person, a name and an explicit consent answer. "No" or no
  answer means that person's audio and any mention is dropped by the existing gateway
  rules. Muse never decides this.
- Muse does not guess who a person is (the existing perceive prompt already forbids it).

### Consent session

Capture needs an active grant for a session. For uploads the commit step creates (or reuses) an
`upload-<date>` session and grants the owner's consent through the existing grants code. Other
participants get a grant only if the user said they agreed. Expiry defaults to "until withdrawn",
matching the current grant model.

### Chat

Frontend only; the `/recall/ask` API is unchanged.

- `AskPanel` is rewritten as a thread of bubbles with a pinned composer.
- Progress steps are driven by the single request's lifecycle (asking, answered, failed). They
  are honest: three fixed phase labels advance on timers while the request is pending, and
  resolve when it returns. We do not claim per-step backend telemetry that does not exist.
- Answer bubble: status badge from the existing `status`, text, `uncertainty_note`, citation
  chips (existing `onCite`), "Why? See evidence" (existing `onWhy`).
- Follow-up pills come from the existing `suggest.ts` groups (code, not model).
- Scope chips from the mockup are **cut** from this slice: they imply server-side filtering that
  the API does not have. Revisit later.
- Empty state: four starter questions from `suggest.ts`.
- Phone: chat becomes a bottom sheet. The map component is reused unchanged.

### Frontend placement

- New `components/AddMemory.tsx` (dialog/side panel) and `api/client.ts` additions.
- Header gets one "Add memory" button (the only edit outside the chat and the new dialog).
- `App.tsx` mounts the dialog and passes `refresh` so the graph reloads after Save.

## Decisions I made (please check)

- **D1.** Preview/commit two-phase API rather than extending `/capture/{kind}`.
- **D2.** No EXIF library dependency beyond `Pillow` for reading EXIF. If Pillow is not
  acceptable we fall back to asking the user for time and place.
- **D3.** Video is deferred. Muse accepts video, but the client has no video path and frame
  extraction needs ffmpeg in the image. Photos, voice (WAV) and text first.
- **D4.** Voice upload accepts WAV only (the ASR contract). Other formats show a clear error
  instead of silent conversion.
- **D5.** Drafts live in memory for 15 minutes, keyed by id, text only.
- **D6.** Scope chips and graph pulse are out.
- **D7.** Progress steps are time-based labels, not backend events.

## Open for the builder

- Exact `draft` JSON schema and field names.
- File size limits (suggest 10 MB image, 32 MB audio, matching the ASR limit).
- Test fixtures: a tiny JPEG with EXIF, a tiny WAV, fakes for Muse in `tests/`.

## Verification

- Backend unit tests for preview and commit with a fake LLM, including: no consent drops
  audio, duplicate upload is rejected, blocked hash is rejected, raw bytes never persist.
- Frontend `npm run check` (type-check plus unit tests) passes.
- Manual run in Docker with live Muse: upload a real photo and a short WAV, answer the
  questions, confirm the new claims appear in the Atlas with provenance.
